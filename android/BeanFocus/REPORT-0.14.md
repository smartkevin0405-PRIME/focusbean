# 0.14 소스 점검: 삼성 인터넷 감지와 브라우저 간섭

2026-11-03 · 소스 0.14-beta / versionCode 14 · minSdk 26 / targetSdk 35

## 결론과 배포 상태

원본 0.13 소스를 공개 저장소에 복구하고, 확인된 중복 탐색과 불확실한 자동 이동을 수정했다.
현재 소스의 테스트와 서명 없는 APK 빌드는 통과했다. **삼성 실기기 차단 성공과 페이지 로딩 속도 개선은 미검증**이다.
연결된 ADB 기기가 없었으며 기존 서명키도 이 작업 공간에 없다. `release/`는 변경하지 않았고,
기존 최신 APK는 0.13이다. 아래의 소스 변경은 기존 설치에 자동 반영되지 않는다.

## 확인한 증거

- 현재 배포 0.13 APK SHA-256: `0142e774ebdb62acc17033fa6fdc154ea0d1ba24d8c4ed2dc823f35e23f40fed`.
- 이전 기기 진단: `com.sec.android.app.sbrowser:id/location_bar_edit_text`에서 YouTube 도메인만 확인,
  경로 미확인, 웹 노드 0, 오른쪽 동작 0. 이는 이번 실행에서 새로 측정한 값이 아니다.
- 0.13의 `BrowserInspector.read`는 주소 ID별 직접 조회 후 최대 180개 UI 노드를 다시 탐색했다.
  경로가 불명확하면 별도 플레이어 탐색(최대 600개)을 실행했다. 클릭 처리에서 이 읽기를 한 뒤
  일반 이벤트 경로에서 다시 읽을 수 있었고 클릭의 첫 읽기는 250ms 제한 밖이었다.
- 기존 코드는 이미 주소의 text/description을 모두 비교하고 전체 경로를 우선했다.
  "도메인 첫 후보에서 탐색 종료"가 원인이었던 것은 아니다.
- `WebView`에서 바로 탐색을 중단하므로 그 아래의 `rootWebArea`가 제공하는 문서 URL을 놓칠 수 있었다.
  또 뒤늦게 만난 주소창 후보가 먼저 읽은 문서 URL보다 높은 점수를 받아 오래된 주소를 채택할 수 있었다.
- 클릭 후 450ms 확인에서 도메인만 보여도 BACK을 요청하는 분기가 있었다.
  브라우저 창 ID는 탭 전환 전후 같을 수 있으므로 이 조건만으로 현재 쇼츠 화면을 증명할 수 없다.

## 수정

1. 주소창과 웹 문서 바깥 UI를 한 번 탐색한다. 이 탐색이 한도 안에서 끝나면 ID별 중복 조회를 생략한다.
   한도에 걸렸을 때는 직접 ID 조회를 유지해 먼 위치의 주소창이나 입력 중인 주소를 놓치지 않게 한다.
2. `WebView`의 얕은 래퍼 아래 `rootWebArea` URL을 제한적으로 읽는다(최대 24개, 깊이 2).
   문서 URL은 주소창보다 우선하며 링크의 목적지를 현재 URL로 취급하지 않는다.
3. 플레이어 보조 검사에 이미 찾은 웹 루트를 넘겨 브라우저 UI 재탐색을 없앤다.
   경로가 확정되거나 웹 루트가 없으면 보조 검사를 하지 않는다. 문서 간 버튼 증거는 합치지 않는다.
4. 일반 이벤트와 2초 주기 검사가 500ms 예산을 공유한다. 이벤트를 하나의 예약 작업으로 합치되
   연속 스크롤 때 예약을 계속 미루지 않는다. 웹 보조 검사는 같은 창에서 최소 5초 간격으로 제한한다.
   클릭 후 확인과 실제 차단 후 이탈 확인은 제한된 별도 확인 경로다.
5. 쇼츠 링크/탭 클릭은 검사 계기로만 사용한다. 현재 경로 또는 플레이어 증거가 확인돼야 BACK을 요청한다.
   HOME 재확인에도 같은 조건을 적용하고, 브라우저 자동 이동 직전 패키지와 창 ID를 다시 확인한다.
   새 클릭은 이전 클릭의 지연 동작을 무효화한다.
6. 차단을 끄면 주기 검사에서도 브라우저 트리를 읽지 않는다. 이벤트 검사도 분류 결과를 관측 기록에
   반영해 이벤트가 2초 주기 검사 예산을 차지했을 때 통계가 누락되는 문제를 방지한다.
7. 진단에 검사 횟수와 최근/평균/최대 검사 소요 시간을 추가한다. 전체 URL·영상 제목은 기록하지 않는다.
   이 시간은 접근성 검사 시간이며 페이지 로딩 시간이나 성능 개선율이 아니다.

## 검증

- Windows: Android Studio JBR 25, SDK API 37, Build Tools 36. javac의 Android bootclasspath,
  D8 min-api 26, aapt2, zipalign으로 전체 앱을 빌드했다. targetSdk는 35를 유지했다.
- Java 테스트 실행 단위 20개, Node 실행 단위 4개, `audit_014.py` 통과.
- 기존 게임·잠금·PiP·설정 보호·통계·XP 회귀 테스트도 포함한다. Android 노드 대역 테스트는
  실제 삼성 접근성 노출이나 프로세스 간 호출 시간을 재현하지 않는다.
- 새 회귀 사례: 중첩 문서 루트, 문서/주소창 순서, 일반 강의와 편집 중 주소 허용,
  웹 노드가 없는 도메인-only 상태, 노드 예산과 핸들 해제, 페이지 링크/프레임의 오판 방지,
  이벤트 폭주/폴링 예산 공유, 클릭 후 불명확 화면에서 차단하지 않기, 빠른 이벤트에도 통계 축적.
- 가상 Chrome 화면(본문 자식 800개): native 노드 3개, child 조회 2개, 직접 ID 조회 0회.
  확정된 문서 URL에서는 본문을 순회하지 않았다. 이것은 가상 노드 연산 수이며 실제 속도 측정이 아니다.
- GitHub의 `Validate BeanFocus source`는 JDK 17/API 35/ECJ 3.37로 같은 테스트와 unsigned 빌드를 수행한다.
  실행 결과는 해당 커밋의 Actions에서 확인한다. 이 작업은 APK를 게시하지 않는다.

## 남은 한계와 실기기 확인

삼성 인터넷이 URL 경로, 문서 루트, 플레이어 노드 어느 것도 제공하지 않으면
접근성 읽기만으로 `/watch`와 `/shorts`를 구분할 수 없다. 이번 변경은 그 정보를 강제로 노출시키지 않는다.
주소창 클릭·포커스 변경·클립보드 복사로 정보를 꺼내는 동작도 추가하지 않았다.
도메인 전체 차단은 하지 않으며, 이 상태는 판별 불가로 남는다.

검사 간격을 늘리면 감지 반응 속도와 비용 사이에 차이가 생긴다. URL 변경 이벤트는 보통 다음
500ms 예산에서 검사하고, 이벤트가 없으면 2초 주기 검사에 의존한다. 플레이어 보조 신호만으로
판정하는 경우 5~6초 이상 늦어질 수 있다. 동작 확인을 위한 실제 타이밍 측정이 필요하다.

같은 삼성 기기와 네트워크에서 접근성 끔 / 0.13 / 0.14를 비교한다.

| 시나리오 | 확인할 결과 |
|---|---|
| 삼성/Chrome 직접 Shorts URL와 사이트 내부 진입 | 현재 쇼츠 증거와 BACK 전달, 계속 남으면 재확인 |
| 일반 강의, 유튜브 홈, 추천 Shorts 카드만 표시 | 자동 BACK/HOME 없이 이용 가능 |
| 주소 입력 후 취소, 탭 전환, 뒤로 가기, 분할 화면 | 다른 페이지/창에 이전 클릭의 동작이 적용되지 않음 |
| 차단 꺼짐, 화면 잠금, 앱 전환 | 불필요한 브라우저 검사와 자동 이동 없음 |
| 같은 페이지 반복 로딩/스크롤 | 페이지 로딩 시간과 접근성 검사 시간/횟수를 별도로 기록 |
| 삼성 도메인-only + 웹 노드 없음 | 판별 불가 상태 유지, 성공으로 보고하지 않음 |

## 참고

Chromium은 Android 웹 접근성 노드를 요청할 때 생성하는 경로와 그 비용을 설명한다.
이는 불필요한 탐색을 줄일 근거이며 이 기기의 지연 원인을 측정해 확정한 자료는 아니다.

- [Chromium Android 접근성 구현](https://chromium.googlesource.com/chromium/src/+/main/docs/accessibility/browser/android.md)
- [Android AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo)
- [Samsung 콘텐츠 차단기 개발 가이드](https://developer.samsung.com/browser/android/adblockers-guide.html)

Samsung 공식 콘텐츠 차단기 연동은 등록/검증을 거치는 별도 접근이다.
이번 버전에 등록되지 않은 확장 기능이나 네트워크 프록시를 추가하지 않았다.
